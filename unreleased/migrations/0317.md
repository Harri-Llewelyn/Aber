### A device has no connection_method column (0317)

1.9.0 deprecated `devices.connection_method`. Every device reaches Aber over Sparkplug B, so the
column said nothing, and the dashboard stopped sending it. 1.10.0 removes it, one minor later, as
[*Deprecation*](../../docs/releases.md#deprecation) asks.

- **The device lane stops admitting it.** `proposable_columns()` is `0202`'s body without it, with
  `0176`'s `search_path` pin restated. `validate_change_proposal()` then refuses a new proposal that
  names it, by name, when it is filed.
- **A proposal filed before the upgrade is refused at approval, never at boot.**
  `approve_proposal()` is `0165`'s body without the column. Its re-check of the patch against the
  allowlist refuses a key the lane no longer admits, as before. The message now ends "reject it,
  and ask for a new proposal without it", and the code is still `invalid_parameter_value`, which
  PostgREST answers 400. Without that re-check the proposal would be applied with the key left out:
  `jsonb_populate_record()` ignores a key with no column. Refusing the boot instead would stop
  db-init on every boot until someone acted, while nobody could reach the dashboard to act. The
  upgrade note gives the query that lists such proposals.
- **Then the column goes, with its values.** A NOTICE in db-init's log says how many devices held a
  value that was not blank. No view, index, constraint or trigger names the column, so nothing is
  rebuilt.
- **The Audit Trail's old rows keep it.** `audit_event_class()` (`0306`) reads the key out of
  `old_data` and `new_data`, never out of the table, so a past change to it is still
  **Configuration**. The classifier is not redeclared.

#### Every boot adds it back, and this file drops it again

`0001` and the files before this one are released and are not edited, so they still name the
column. `0001` creates it, and its `ADD COLUMN IF NOT EXISTS` adds it back, empty, on every boot.
`0001` and `0165` declare `approve_proposal()` with it, and `0001` and `0202` declare
`proposable_columns()` with it. Each of them replays with the column in place. This file then
redeclares both functions and drops the column again. The drop checks that the column exists first,
so the file also replays on its own.

That uses one attribute number of `devices` on every boot. PostgreSQL never reuses a dropped
column's number, and a table has at most 1,600, dropped ones included. `devices` has 23 columns, so
about 1,570 boots remain. db-init runs on each install and upgrade, so a site uses a few a year; a
development stack that redeploys db-init many times a day uses them faster. The next fold takes the
column out of `0001`, and the cost stops there.

`approve_quarantined_device()` (`0293`) still names the column in a comment about the merge, and is
not redeclared for a comment alone.

The self-check asserts that the column is gone, that the device lane does not admit it, that
`proposable_columns()` keeps its pin, and that the live `approve_proposal()` does not name it, still
re-checks the patch and asks for a second factor, and is `SECURITY DEFINER` with its search path
pinned. `test_a_device_has_no_connection_method_column.py` rebuilds 1.9.0's column inside each test's
transaction. It holds the refusals at filing and at approval, the rejection, the upgrade note's query,
the count in the log, and two boots in a row. Drift check 527 holds that no file after the released
ones names the column but `0317`, that the API reference documents it on neither `Device` nor
`DeviceWrite`, that no code reads it but the Approvals page's label for an old proposal, and that the
upgrade note's query is the suite's.
