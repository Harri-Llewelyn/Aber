### A search asks about the tombstones once, and can limit each kind (0330)

Two things made a search of every entity slow. Each tombstone cost about 0.1 ms, because the policy that lets a
caller read it asked `has_authority()` for each row. And one kind could fill
[`find_entities()`' answer](0321.md), so the search bar then read each other kind apart.

#### Four policies ask once for the statement

`retired_entities_select_privileged` called `has_authority()` bare, and the planner runs a bare call for each row
it reads. In a sub-select the call is an initplan, run once. `0177` and `0204` made the policies they restate so.
Three more that `entity_directory` reads were written the same way, and this file restates them too:
`captures_select_privileged`, `backups_select_administrator` and `machine_principals_select_admin_or_auditor`.
Each admits whom it did.

`0001` still states the per-row form, with `p_stated_by` naming this file (`STATED_LATER`). It creates one only
where it is missing, so a fresh install meets the old form between the two files and a later boot never does. The
self-check reads the live policies and fails on a call outside a sub-select.

#### A limit of each kind

`find_entities(p_query, p_limit, p_per_kind)` answers at most `p_per_kind` rows of each kind. A kind's rows go by:

1. **How the text names them:** a whole id, a whole name, the start of an id, part of a name.
2. **Their state:** active, archived, retired. The three are in that order by their letters.
3. **Their name,** a shorter one first, so *Press 2* is kept before *Press 10*. The search bar lists names in the
   order people read numbers (`shortlist()`), and ten kept by letters alone would be *Press 1* and *10* to *18*.

`p_limit` still holds the total, and the state then counts in the order of the whole answer too. A number below 1 is
1, as it is for `p_limit`. **Without `p_per_kind` the answer is 0321's, row for row:** the suite reads 0321's body
out of that file and runs it beside this one, for each role.

The search bar asks for 10 of a kind and 200 in all. There are ten kinds, so the total never cuts one short.

#### One form

A new argument is a new signature, and PostgREST calls by argument names: with both forms declared, a call naming
`p_query` and `p_limit` is neither's. So the two-argument form is dropped, in the transaction that declares the new
one.

**`0321` declares the two-argument form again on every boot,** and this file drops it again. Between the two a search
answers an error. Measured through PostgREST while `0321` to `0330` were replayed as db-init replays them: 0.2 to 0.4
seconds on a quiet laptop and 0.8 on a busy one, the end of it PostgREST's schema cache. The first boot of an upgrade
has no such gap, because the two-argument form alone is there until this file runs. The self-check asks only that
the two-argument form is gone, so a later file may add another argument the same way.

#### How long it takes

Measured with 2,000 tombstones, 4,950 live and 50 archived devices, 400 gateways, 200 cells and 1,500 metrics, as an
Administrator, on a quiet laptop. The median of 20, the two forms taking turns.

| Read | Before | After |
| :--- | :--- | :--- |
| `SELECT * FROM entity_directory` | 230 ms | 42 ms |
| `SELECT * FROM retired_entities` | 207 ms | 12 ms |
| `find_entities()` by an id | 252 ms | 62 ms |
| `find_entities()` by a name one row has | 249 ms | 55 ms |
| `find_entities()` by a text every name holds | 249 ms | 76 ms |
| `find_entities()` by an id, as an Operator, who reads no tombstone | 231 ms | 49 ms |
| With 10 of a kind, by an id | | 61 ms |
| With 10 of a kind, by a text every name holds | | 73 ms |

Placing each row within its kind costs a sort of the rows found, whether or not a limit is asked for: 19 ms where
9,620 rows are, and nothing to notice where a few are.

`test_a_search_asks_about_the_tombstones_once.py` (db lane) holds the limit, the answer without it, the one form and
the four policies. Mirror check `169` holds the limit and the order to the search bar's.
